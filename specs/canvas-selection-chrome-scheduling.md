# 画布选中与起拖交互卡顿治理（原：选中反馈与生成面板调度）

> 文件名沿用历史名称；本 Spec 的范围已从「选中反馈/面板调度」扩展为「选中与起拖链路的卡顿治理」。

## 1. 目标

1. 点击选中任意节点、以及按住节点开始拖动时，画布不出现可见的整体卡顿；生成中的流光描边在长任务期间不冻结。
2. 选中反馈（节点描边、节点工具条）与生成面板仍在同一次提交内呈现，不出现「描边/工具条先出、面板后出」。
3. 卡顿治理以消除同步主线程长任务与主线程逐帧动画为目标，不以「缩短面板挂载时间」为唯一目标。

## 2. 范围

### 2.1 包含

- 选中链路的同步提交成本：选中状态提交、节点工具条挂载、生成面板挂载。
- 起拖链路：React Flow 起拖时的选中、拖动会话初始化、历史压栈、交互态切换。
- 流光描边动画的实现方式：连接目标高亮、Agent 入口按钮共用的描边 recipe（生成浮层曾接入，2026-11-01 改为纯色深底）。

### 2.2 不包含

- 编辑类面板（帧序列、片段截取、音频截取、打光、多视角、全景、标注、裁剪）的挂载策略。
- 媒体渲染管线（LOD、加载调度器）与连线高亮。
- ~~选中描边改由节点包装元素 CSS 驱动的节点 props 契约调整（原 4.3，仍暂不实施）。~~ 2026-10-31：已作为 5.5 候选 A（5.6）提前实施完成，移出非目标。
- 框选手势会话本身的性能（已有独立 Spec）。

## 3. 根因与证据

### 3.1 修订说明（2026-10-31）

原结论「选中延迟主要来自生成面板同步挂载」不完整，已被用户实测推翻：

- 只有工具条、没有生成面板的节点，点击也会卡一下；
- 按住节点（不显示工具栏和生成面板）、移动第一下，也会卡一次。

因此根因需要扩展为「选中/起拖链路上的同步主线程工作 + 流光描边的主线程逐帧动画」。面板是生成节点上最大的一项，但不是唯一原因；起拖路径的卡顿与面板无关。

### 3.2 已验证事实

1. **起拖时先选中，再起拖，同一事件。** React Flow 默认 `selectNodesOnDrag=true`（本项目未覆盖），`nodeDragThreshold=1`；节点可选中且可拖动时，拖动 `startDrag` 内先调用内部 `handleNodeClick`（选中），再调用 `onNodeDragStart`。若节点此前已选中，则起拖没有选中变更。
2. **起拖回调同一批执行多项画布级工作。** `handleNodeDragStart` 内依次执行：`dragSession.begin`（构建拖动基线与吸附目标、对整棵画布根做 DOM 查询、写入首帧、隐藏标签层）、`pushHistory(takeCanvasSnapshot())`、`buildGroupHitIndex`、交互态切到 `node-drag`、清空 `dragOverGroup`。
3. **起拖路径中 chrome 被跳过，但工作已发生。** 交互态在同一次渲染中已是 `node-drag`，`showSelectionChrome=false`，工具条/生成面板不会挂载（或同帧挂载后立即卸载），用户看不到 chrome；但选中提交、拖动初始化、交互态切换均已执行。「看不见」不等于「没有做」。
4. **流光描边是主线程动画（5.3 前的实现，现已被可合成实现替换）。** 旧 `.generation-border` 使用 `@property --lime-flow-ring-angle` 角度动画驱动 `conic-gradient`，并用 `mask-composite: exclude` 挖出 1.5px 描边；该动画无法交给合成器，每帧需要主线程样式重算与重绘。同一 recipe 还用于 `.node-body.node-connect-ok::before` 与 `.agent-flow-button::before`。
5. **既有点击选中测量（42 节点，开发模式）仍然有效，但只覆盖点击路径的 React 提交。**

| 节点类型 | 生成面板 | 点击相关提交 actualDuration | 点击 → 选中生效 |
| --- | --- | --- | --- |
| 文本 | TextGenerationPanel | 29–38ms | 80–93ms |
| 图片（上传来源） | 无 | 20.5ms | 33.2ms |
| 图片（生成来源） | ImageGenerationPanel | 60.3ms | 116.3ms |
| 图片（生成来源切换） | ImageGenerationPanel 重挂 | 92.8ms | 153.8ms |
| 视频（上传来源） | 无 | 28.7ms | 56.7ms |
| 视频（生成来源） | VideoGenerationPanel | 52.3ms | 142.1ms |
| 视频（生成来源切换） | VideoGenerationPanel 重挂 | 214.6ms（另有 72.2ms、78.3ms 提交） | — |

> 表中 actualDuration 只统计 React 提交，不含样式/绘制与提交后的后续任务；3.3 的 129 节点端到端测量显著更大，不能把该表当作端到端成本。

6. **修正（2026-10-31，3.3 实测）：原「单次点击成本与节点总数无关」不成立，仅对 42 节点下的 React actualDuration 成立。** 同一节点类型的端到端对比：1 节点点击文本约 42ms、无长任务；129 节点同操作约 130ms（128–131ms 长任务 + 52–53ms 后续任务）。起拖同样随规模增长：1 节点起拖约 20ms 工作、无长任务；129 节点起拖 67–77ms 长任务（chrome 已隐藏，与面板无关）。
7. 生成面板挂载 DOM 规模约 10–24KB；4.2 已消除面板挂载写回（见 5.2）。

### 3.3 trace 归因结果（2026-10-31 探针项目实测）

**方法与环境**（已验证）：

- 载体：应用内新建的探针项目，129 节点 = 128 个文本节点（600×338，7 轮 Ctrl+A/Ctrl+D 级联生成、大量重叠）+ 1 个音频节点；测后已通过应用 UI 删除，未打开用户真实项目。
- 环境：dev 构建（Next dev），应用内浏览器面板（Chromium），视口约 1550×1058，缩放 0.6944；无 CPU 节流。
- 事件：点击为 `PointerEvent` 序列；节点拖动为 `MouseEvent` 序列（与 d3-drag 监听一致）。
- 仪器：PerformanceObserver(`longtask`) + rAF 间隔采样 + MutationObserver（childList/class/`data-interaction`）+ 事件相位标记。表中时间为事件派发后的墙钟时间，不是 React Profiler 的 actualDuration。

**结果**（129 节点画布）：

| 场景 | 长任务 | 帧最大间隔 | DOM/时间点 |
| --- | --- | --- | --- |
| 点击未选中文本（面板未开） | 128–131ms + 52–53ms | 150–183ms | 选中/工具条/面板同批出现 ≈138–142ms；+35 元素（3440→3475） |
| 点击已选中文本 | 无 | ≈17ms | 无变化 |
| 文本 A→B（面板重挂） | 129ms + 57ms | — | 面板重挂 |
| 点击空白（取消选中、面板关闭） | 无 | ≈50ms | 取消提交 ≈18–31ms |
| 点击音频（仅工具条、无面板） | 52–53ms（提交 20–28ms） | ≈50ms | 1 工具条、0 面板 |
| Ctrl+A 选中 129 节点 | 273ms + 109ms | 336ms | +642 元素（≈5/节点） |
| 拖动未选中文本 | 起拖 77ms；拖停 161ms + 52ms | 100 / 183ms | — |
| 拖动已选中文本（面板开启） | 起拖 67ms；拖停 146ms + 52ms | 83 / 167ms | — |
| 拖动已选中音频（仅工具条） | 起拖 68ms；拖停 70ms | — | — |
| 拖动 129 节点多选 | 起拖 73ms；拖停 100ms + 66ms | 83 / 150ms | — |
| 空闲（文本已选中、面板开启） | 无 | 稳定 16.6ms | — |

**归因**（同画布差值，已验证）：

1. 文本 vs 音频点击（同一选中提交路径）：面板挂载增量 ≈100ms；仅工具条路径本身 ≈75–80ms（提交 20–28ms + 后续任务 52–53ms）。
2. 起拖阶段 chrome 已隐藏，文本（67–77ms）与音频（68ms）长任务基本相同 → 起拖成本与面板无关，来自选中提交/拖动初始化/历史快照/交互态切换的叠加。
3. 拖停：文本 146–161ms、音频 70ms → 拖停时面板重挂约增加 80–90ms；音频拖停仍有 70ms 的规模相关成本。
4. 规模效应（同一节点类型对比）：点击文本 1 节点 ≈42ms（无长任务）→ 129 节点 ≈130ms；起拖文本 1 节点 ≈20ms → 129 节点 67–77ms。起拖已排除面板，说明画布级同步工作随节点数增长；面板挂载不是规模效应的来源。
5. 画布级样式/绘制同样随节点数放大：在 128 节点画布上直接给全部节点加选中类（不经过 React）产生 116.7ms 帧间隔；单节点约 50ms。2026-10-31 未节流复测（3.3.2）未复现该数值：同样的全量选中类变更为 recalc 中位 2.3–20.8ms、帧中位 16.5–16.7ms；本行不再作为量级依据。
6. 空闲时无长任务、帧稳定 16.6ms；运行页中 5.3 的 `.lime-ring__spin`（`lime-flow-spin`）已生效、旧 `::before` 动画为 `none`，未观测到持续主线程成本（运行页证据，非逐帧火焰图）。

**结论**：面板挂载仍是生成节点点击/拖停上的最大单项（≈100ms），但仅工具条节点（≈75–80ms）与起拖（≈70ms）在 129 节点画布上已有可观同步成本，且随节点数增长。5.4 只能消除面板项；5.5 必须处理画布级工作与选中提交的渲染/样式范围。3.2 第 6 条「点击成本与节点数无关」按本结果修正。

**仍未验证（instrumentation 限制）**：

- 用户真实 141 节点画布上的绝对值：按要求未打开真实项目；探针为合成级联且节点高度重叠，与真实构图不同。
- 起拖约 70ms 内部「选中提交 / 拖动初始化 / 历史快照 / 交互态切换」各自占比：无 React Profiler，只有端到端数据。
- 点击路径内部 React 提交与样式/绘制的拆分：同上。
- 生产构建；真实鼠标事件（本次为合成派发，输入管线时序可能与真实指针不同）。
- 5.3 描边的逐帧主线程成本（本次只有空转长任务/帧间隔与早前独立探针的 TaskDuration/RecalcStyle 指标，未做应用内逐帧火焰图）；多生成节点并存的 GPU/内存开销。

> 2026-10-31 补充：步骤 0 已用 React Profiler + User Timing 分离各段（见 3.3.1）。本节端到端数字未重测；其合成事件探针为定位节点做过同步坐标读取，可能包含探针自身的强制布局（推断，未复核），引用绝对值时以 3.3.1 为准。候选 B 的样式补测与未节流验收复测见 3.3.2/3.3.3；116.7ms 类变更实验未复现。

### 3.3.1 5.5 步骤 0：分段归因（2026-10-31，dev-only User Timing + React Profiler）

**方法与口径**（已验证）：

- 仪器：仅 dev 生效的 User Timing（`canvas.select.commit`、`canvas.canvasderived`、`canvas.interaction.dispatch`、`canvas.dragbegin.*`、`canvas.dragstop.*`）、仅 dev 的 React `Profiler`（`canvas.shell` 包住 `CanvasWithKeyboard`，`canvas.flow` 包住 `<ReactFlow>`）、节点组件渲染计数，以及 `longtask` / `long-animation-frame` 观察。归因完成后所有仪器与调用点已移除。
- 干净测量：节点坐标在测量窗口外预读，窗口内只派发合成事件。上一轮探针在窗口内读取 `getBoundingClientRect()` 定位（单次 39–50ms），已证实会触发整画布排版并污染长任务，本轮不计入。
- 矩阵：2 节点探针（1 文本 + 1 音频）vs 129 节点探针（128 文本 + 1 音频）；点击音频/文本、起拖音频/文本、拖停音频/文本、Ctrl+A。dev 构建 + StrictMode，`actualDuration` 含 StrictMode 双渲染，绝对值高于生产。
- 环境限制：本轮预览窗格失焦（`document.hasFocus()` 为 false，rAF ≈1fps），按 7.4 不以帧间隔/强制布局作为证据；React Profiler 与 User Timing 不受渲染节流影响。§3.3 当时空闲帧为稳定 16.6ms（未节流），两轮环境不同，长任务与帧间隔不可直接拼接。
- 两个探针项目已通过应用 API 删除；未打开用户真实项目。

**结果**（129 节点，dev；React 为 shell `actualDuration` 合计）：

**长任务内占比**（按同任务实测拆分）：

- 点击文本 128ms：React ≈29%，面板 JS + ProseMirror 强制布局 ≈48%，其余（React Flow/浏览器提交与样式）≈23%。
- 拖停音频 75ms：React ≈35–40%，d3 指针读取/整画布排版与样式 ≈60%。
- 拖停文本 133ms：React ≈32%，面板重挂 ≈47%，其余 ≈21%。
- Ctrl+A 273ms：React ≈70%，其余 ≈30%（样式/绘制，§3.3 的 116.7ms 类变更实验佐证）。
- 起拖：React ≈31ms，任务未达长任务阈值（>60% 为 React）。

**归因**：

1. 本仓库交互簿记（选中提交、画布派生、交互态派发、起拖基线/快照/DOM 捕获、拖停提交）在 129 节点上合计 ≤2.2ms。工作项 3（起拖初始化）与 4（拖停提交）没有可优化空间；工作项 2 的「几何投影/壳层重渲染」部分也只有 ≤5–7ms（Ctrl+A 时 shell 与 flow 差 0.6ms，派生缓存未命中 ≤5.2ms）。
2. 随节点数增长的主要 JS 成本是**节点组件因 `selected` 重渲染**：单次操作 10–30ms，Ctrl+A 191ms（127 个文本节点逐个重渲染，节点主体含 Tiptap 相关子树）。这正是 5.6 的范围，而不是 5.5 草案原设想的派生/壳层。
3. 面板挂载仍是生成节点点击/拖停的最大单项（≈100ms；其中 React 外 Tiptap/ProseMirror 约 40ms JS + 22ms 强制布局），归 5.4。
4. 拖停的 React 外残余（音频 ≈45ms、文本 ≈92ms）：源码确认 d3-drag 在 gesture end 读取容器 rect，129 节点上会触发整画布排版；文本另含面板重挂。当前窗格节流，残余绝对值只作方向；「整画布排版随节点数放大」另有 §3.3 的独立证据（128 节点加选中类 → 116.7ms 帧间隔）。
5. 样式/绘制本轮无法新增有效数据（窗格节流）；§3.3 的 116.7ms 类变更实验仍是唯一有效证据，量级不可忽略。按步骤 0 要求，若走样式路线，必须先做独立探针的 recalc 对比。
6. 未定位：点击或拖动音频后约 500–640ms 出现一次 52–54ms 任务（文本拖停窗口内未出现）。疑似音频波形/峰值计算或存档调度，未验证；它不影响交互提交归因，但影响「操作后无长任务」的验收口径。

**对 5.5 的影响**：本轮干净测量中，三组验收操作只有「仅工具条拖停」仍超 50ms（75ms，且绝对值受节流影响）；点击仅工具条与起拖均无长任务，其 JS 部分分别为 9–27ms、31–32ms。旧 §3.3 的 52–77ms 端到端值可能含探针定位读取（推断，未复核），应以未节流窗口复测为准。

> 2026-10-31 补测：窗格恢复未节流后的验收复测见 3.3.3（点击仅工具条无长任务、起拖 54–61ms、仅工具条拖停 58ms）；样式/绘制补测见 3.3.2。

### 3.3.2 5.5 候选 B：样式/绘制补测（2026-10-31，129 节点，未节流）

**方法与环境**（已验证）：

- 载体：应用内探针项目「Perf Probe 5.5 Style」（128 文本 + 1 音频，与 3.3/3.3.1 同一节点矩阵与视口），从已登录的应用会话通过同源 API 创建，测后经 API 删除；未打开、未复制用户真实项目，未读取任何凭据文件。

- 与候选 B 原文的差异：原计划「独立探针页」；因窗格已恢复未节流，改用应用内探针项目页，以获得真实编译 CSS 与组件结构（独立静态页需复制 CSS，可能改变级联）。该差异记录在此。

| 策略 | sync 中位（min–max） | frame 中位 / 最大 |
| --- | --- | --- |

4. §3.3 第 5 条「128 节点加选中类 → 116.7ms 帧间隔」未复现：同样的全量类变更本轮为 sync 2.3–20.8ms、frame 中位 16.5–16.7ms（最大 33ms）。该行不再作为量级依据；差异原因未查明（可能含当时的其他任务或布局/绘制差异，未验证）。
5. 交互态切换的 ≈30ms 与 3.3.3 的起拖/拖停长任务在时间上重合；按「同操作包含该属性切换」推断工作项 1 可消除其中约 30ms，但未逐段拆解（推断）。
6. 帧间隔只覆盖下一帧；选中描边/阴影的真实绘制成本未用 GPU/绘制指标单独拆分（未验证）。

### 3.4 结论

「选中/起拖卡顿」= 交互路径上的同步主线程工作（选中提交 + chrome 挂载 + 起拖初始化 + 交互态切换）叠加流光描边的主线程逐帧动画。面板挂载是生成节点上最大单项（129 节点画布 ≈100ms），但不是唯一原因：仅工具条节点仍有 ≈75–80ms，起拖 ≈70ms 且与面板无关，二者都随画布节点数增长（1→129 节点，点击文本 42→130ms、起拖 ~20→67–77ms）。因此本 Spec 不能只解决面板：5.4 消除面板项，5.5 必须针对画布级同步工作与选中提交的渲染/样式范围。流光既是长任务的受害者（长任务期间停帧），也是持续的主线程预算消耗者（5.3 已改为合成器动画）。

### 3.5 外部参照：即梦（仅作对照，不作为方案依据）

对用户已登录的即梦画布（React Flow 架构，53 节点）做被动观察与一次合成点击：

- 选中类名与选中工具条在同一批 DOM 变更内生效；工具条 DOM 约 66.7KB；点击后约 65ms 完成（生产构建）。
- 取消选中后元素数回到 1700，工具条完全卸载。

结论：即梦**没有**把重工具条延后挂载，而是让单次点击的总工作量足够低（生产构建）。说明同步挂载重 chrome 也可以做到可接受，前提是其余提交成本足够小。测量局限：合成为一次性派发，MutationObserver 时间戳为投递时刻、不能证明同一回调内各变更的先后；无法获知其构建配置与内部状态管理。

## 4. 技术影响

1. **流光描边**：`web/src/styles/globals.css` 的三处共用 recipe；改为「父层静态 mask + 子层静态 conic-gradient 仅 transform 旋转」后，影响生成浮层、连接目标高亮、Agent 入口按钮三处视觉与动画实现。需要验证圆角、非方形节点、缩放下 1.5px 描边、明暗主题、`prefers-reduced-motion`。
2. **生成面板宿主复用（若采纳 5.4）**：三类面板的生命周期从「选中即挂载、取消即卸载」改为「宿主常驻、按目标切换」；影响 Tiptap 实例生命周期、mention 建议、undo/焦点语义、参考卡片媒体 URL 解析与订阅。隐藏状态下必须停掉重活。
3. **起拖路径**：`drag-preview-session.begin`、`CanvasSurface` 接线的 `handleNodeDragStart`、交互状态机；可能涉及 DOM 快照按 id 定位/缓存、减少选中提交重渲染范围、合并交互态写入。具体改动以 trace 归因为前提。
4. **选中提交**：`CanvasSurface` 的整画布渲染范围与工具条挂载成本；若需把选中态订阅从画布壳层拆出，属于架构调整，另行评估（与原 4.3 同类问题）。
5. **明确不做**：延迟挂载、`useDeferredValue`/`startTransition` 等拆分 UI 时序的方案已证伪，不再采用。

## 5. 方案

### 5.1 已撤销：选中面板延迟挂载

> 2026-10-31 用户实测反馈：工具栏先出现、生成面板约 1s 后才出现，体验不可接受；本方案撤销。

- 原方案：`useDeferredValue` 将面板挂载推迟到后台渲染，选中提交只呈现描边与工具条（曾实现于 `hooks/use-deferred-panel-target.ts`）。
- 撤销原因：后台渲染在重负载画布（视频播放、加载、生成任务）上会被持续抢占，挂载间隔不可控；「描边先出、面板后出」的割裂感比同步挂载的整体延迟更差。
- 现方案：生成面板与选中态在同一次提交挂载（恢复同步挂载）；选中延迟由 4.2 消除面板挂载写回后的额外整画布提交来降低，不再拆分渲染时序。

### 5.2 已完成：面板挂载不得写回业务数据

- 现状：`ImageGenerationPanel` / `VideoGenerationPanel` 的挂载 effect 会在悬空 modelKey、字段超范围、refMode 不合法时写回 `genSettings`。
- 目标：选中等价于「查看」，不修改节点数据。纠偏规则下沉到数据层：
  - 在生成设置写入入口统一归一化；
  - 模型目录变化时由画布级归一化一次性处理受影响节点，不依赖选中。
- 收益：消除选中后的额外整画布提交；纠偏不再依赖「节点恰好被选中」。
- 影响面：生成设置写入路径、模型目录订阅、图片/视频/Agent 共用的参考模式规则（复用现有共享实现，不复制规则）。
- 实现：新增纯归一化 `shared/gen-settings-normalize.ts`、写入入口 `shared/gen-settings.ts`、画布级 `hooks/use-gen-settings-normalization.ts`；三类面板删除挂载写回 effect；模型目录构建收敛到 `shared/model-catalog.ts`；视频面板改为派生生效 `refMode`（不再为纠偏写回）。画布级归一化订阅两类数据源：模型目录变化时全画布归一化（含空节点占位比例），连线变化时只归一化设置值（`refMode` 可用范围随上游参考变化），不重排占位框。

### 5.3 已确认（2026-10-31 用户指示「先做 5.3」）：流光描边改可合成

**方案**：父层保留静态描边 mask（`border-radius: inherit`、1.5px 环、`mask-composite: exclude`），内部放一个足够大的方形层承载静态 `conic-gradient`，只对内部层的 `transform` 做旋转动画；父层 mask 将可见区域裁成描边环。三处共用同一实现，替换 `@property` 角度动画。

**理由**：transform 旋转可交给合成器；长任务期间描边继续运动；每帧不再触发主线程样式重算/重绘；连接目标与 Agent 按钮同步受益。

**待验证**：非方形节点的旋转层覆盖尺寸；圆角与 1.5px 环的视觉一致性；明暗主题；reduced-motion；多生成节点并存的 GPU/内存开销。

**验收**：见 8.1、8.2、8.6。

**验证结果（2026-10-31）**：实现与独立探针数据见第 10 节「5.3 已实现」；深/浅两种底色、非方形、圆角与 reduced-motion 已比对，画布缩放与多节点 GPU/内存开销未测。

### 5.4 已实施（2026-10-31，用户指示「把未做的都做掉」）：生成面板宿主复用

**方案**：同类型面板宿主常驻画布层，选中只切换 `nodeId`，不重建 Tiptap/Radix/参考卡片；面板仍在选中时出现，取消选中立即不显示，不做延迟挂载。

**需要设计**：

- 编辑器实例复用后的内容同步（切换目标时 `setContent` 的时机与来源）；
- mention 建议、undo 历史、焦点与选区语义；
- 隐藏状态下停止媒体 URL 解析、订阅与轮询；
- 宿主常驻的内存与订阅边界；是否按类型各保留一个宿主。

**收益**：把面板挂载从「每次选中」降为「首次使用一次」，消除生成节点上最大的同步成本。

**风险**：生命周期语义变化；编辑器实例复用可能引入内容串台/焦点问题。若采纳，建议单独 Spec 或在本 Spec 中单列确认。

**实现（2026-10-31，工作区未提交）**：

- 新增 `panels/GenerationPanelHost.tsx`：图片 / 视频 / 文本三类面板各保留一个槽位实例；槽位从未使用过时不挂载，使用过则常驻。可见槽位 `display:contents`（不产生额外盒模型，定位与旧挂载一致），隐藏槽位 `display:none`；定位仍由 `NodeToolbar`（Bottom / center / 12px）承担，锚定最后一个目标节点，取消选中后面板全部隐藏但实例保留。目标节点被删除时，宿主从记忆（锚点与各类型槽位）中剔除该节点，槽位随之卸载（目标已不存在，编辑器状态无需保留）；锚点被删除但其他槽位仍存在时改挂该槽位继续常驻，宿主本身常驻，下一次目标重新挂载槽位。
- 面板新增 `active` prop：隐藏时停止 `genSettings`、上游引用、生成态订阅，卸载参考区与操作区（Radix 浮层关闭、参考卡片停止媒体订阅），只保留 Tiptap 编辑器实例、文档与撤销栈；重新可见时只挂回 chrome。
- `MentionPrompt` 常驻后按 `nodeId` 切目标：`useLayoutEffect` 以新目标的文本重建 `EditorState`（插件状态与 history 整体重建，撤销栈不跨目标；不经过 Tiptap `dispatchTransaction`，不反写节点数据），避免新目标先闪一帧旧提示词；隐藏时关闭 @ 候选并失焦，内容留给同一目标再次显示。
- 编辑器重建移出 React 提交阶段（2026-10-31 修复）：Tiptap `ReactRenderer` 在编辑器已有未处理同步更新时以 `flushSync` 创建 mention NodeView；若在 `useLayoutEffect` 内 `updateState`，等于在 React 提交阶段同步刷新，会触发「flushSync was called from inside a lifecycle method」。现改为 `queueMicrotask` 延迟重建：同一提交内多次切换合并，以最后一次渲染的 `nodeId / value / references` 为准，并以 `editor.isDestroyed` 守卫。
- 文档归属不变量：重建延迟到微任务后，被动 effect 会在重建前执行；此时文档仍属于上一个目标，若内容同步 / 引用清理 effect 用新目标的 `references / onChange` 去改旧文档，会删掉旧目标的 chip 并把空文本回写成新目标的提示词。`contentTargetRef` 记录文档当前承载的目标（重建完成时更新），两个内容写入 effect 在归属不符时直接返回。

## 6. 业务规则

1. 选中反馈（描边、工具条）与生成面板在同一次提交内呈现，不做延迟调度。
2. 面板只对应「当前唯一选中目标」；取消选中或切换目标时立即不显示旧目标的面板。5.4 已实施：宿主按类型常驻，隐藏时卸载 chrome 但保留编辑器实例与内容；目标节点被删除时其槽位卸载，其他仍存在的槽位保留。
3. 选中操作不得写回节点数据。
4. 生成设置纠偏规则不变，只迁移执行时机（已按 5.2 实现）。
5. 编辑类面板的挂载策略不变。
6. 流光描边不得使用主线程逐帧动画；连接目标高亮、Agent 入口按钮共用同一可合成实现（生成浮层自 2026-11-01 起改为纯色深底，不再接入）。
7. 起拖路径不得执行与当前交互无关的全画布同步工作；具体边界以 trace 归因为准。

## 7. 异常与边界

1. 流光：非方形节点、圆角嵌套、缩放下的 1.5px 描边、明暗主题、reduced-motion、多个生成节点并存。
2. 起拖：节点此前已选中（无选中变更）、多选拖动、组成员随组拖动（dragItems 包含成员）、修饰键状态变化。
3. 面板宿主复用（已实施）：目标切换时的内容串台、焦点/undo、隐藏状态下的副作用与订阅泄漏、生成中切换目标。已处理：切换目标重建 `EditorState`（history 不跨目标）、重建改在微任务中执行（不在 React 提交阶段构造 mention NodeView，避免 `flushSync` 警告）、内容同步与引用清理按文档归属守卫跳过（避免用新目标的引用清理旧文档并回写新目标）、隐藏时关闭 @ 候选并失焦、停止上游/生成态订阅并卸载参考区与操作区；基础显隐与复用已在浏览器走查。未覆盖：生成任务进行中切换目标的端到端走查。
4. 测量：开发模式与生产构建差异；预览面板失焦时 rAF/Event Timing 被节流，不作为依据；不以开发模式绝对值作为唯一验收标准。2026-10-31 补测时窗格已恢复未节流（60fps），3.3.3 是该环境下的验收基线；3.3.1 的帧间隔数据仅作节流环境记录。

## 8. 验收标准

1. 在重负载画布上，点击生成节点、点击仅工具条节点、按住起拖三组操作均无可见的整画布冻结；trace 中不出现超过约定阈值的主线程长任务（阈值见 9.2）。
2. 生成中的流光描边在选中/起拖提交期间持续运动，不出现停帧。
3. 选中描边、工具条与生成面板仍在同一次提交呈现，无「工具条先出、面板后出」。
4. 切换/取消选中不显示旧面板。
5. 选中任意节点不产生 `genSettings` 写回（回归）。
6. 流光三处在明暗主题、非方形节点、圆角、缩放下与现实现视觉一致；reduced-motion 下静止。
7. `tsc`、ESLint、相关测试通过；新增/调整逻辑有测试覆盖。
8. 测量结果（trace 摘要、环境、画布规模）记录到「当前状态」。
