## 目标

1. 消除画布首次进入（尤其是 0.1 缩放）后拖动时的掉帧：不再因为视口内大量图片同时解码**全分辨率原图**而阻塞主线程，目标恢复到稳定 60 fps。
2. 画布图片按「屏幕实际像素需求」请求服务端派生档位，形成分辨率 LOD；缩放、DPR、节点尺寸变化时按行业惯例**延迟换档**并保留旧图，避免闪烁与抖动。
3. 高缩放、导出、标注、裁剪、网格拆分、下载、预览、生成等需要真实像素的路径继续使用原图，画质不降级。
4. 前后端共用一套档位契约，URL 有界且稳定，避免每个缩放值产生一个新的缓存键。

## 背景与调查结论

### 已验证事实（2026-10-22，本机 headful Chrome + CDP 实测）

- 首次进入画布、视口缩放为 0.1 时开始拖动：帧间隔 p50 为 **33.3 ms**（约 30 fps），明显不跟手。
- 不刷新页面，等待约 3–5 秒让图片加载/解码队列排空后再次拖动：p50 恢复 **16.7 ms**（60 fps）。切到其他标签页再切回、以及在同一标签页单纯等待，得到相同结果；因此「切标签」只是**给解码队列留出了时间**，不是根因的修复手段。
- 首次拖动期间画布内 `<img>` 数量从 25 增至 112；共 **91 个媒体**、约 **152.6 MP** 在拖动过程中完成加载/解码。
- 根因链：
  1. `minZoom = 0.1`，且 `mediaLoadPriority` 以「屏幕矩形是否与视口相交」判定优先级；0.1 缩放时几乎所有节点都在视口内，全部被判为优先级 0。
  2. `prepareImage` 对每个 URL 先加载原图，再 `decode()`；调度器并发上限 4，但 91 张全分辨率图片会在拖动期间持续解码。
  3. 解码是主线程/合成器的高开销工作，与每次 `transform` 更新叠加，直接拉低帧率；队列排空后帧率恢复。
- `next/image` 默认 loader 在抓取 `src` 时**不转发请求头**（Next.js 官方文档明确说明；受保护图片需 `unoptimized`），而 `/api/files/*` 依赖会话 Cookie / Bearer 鉴权，因此默认 `next/image` 不能直接用于画布图片；其 `srcset`/`sizes` 又基于布局宽度与 DPR，不感知画布的 CSS transform 缩放。
- 服务端 `?w=` 管线已经存在并经过验证：鉴权与归属检查、sharp/ffmpeg 媒体池、请求单飞、原子落盘、`immutable` 长缓存、固定档位与向上取整、派生产物随源删除。
- 画布图片当前使用 `fileRefUrl(src)` 的**原图 URL**，没有 `?w=`；视频海报已有 `?w=1280` 先例。

### 未验证推测

- 浏览器在标签页隐藏时暂停 `requestAnimationFrame`，以及切回时合成器重新分块的细节；这些不影响本方案，也不需要依赖。
- 生产多用户规模下，大量首次访问对 sharp 池造成的排队时长；需在实现后按验收口径实测并记录，本 Spec 不以 NAS 单机量级作为设计上限。

### 结论

用「按屏幕像素选档 + 档位延迟切换 + 旧图占位」的分辨率 LOD 替代「一律全分辨率」。这与 tldraw、Figma 等画布产品的公开做法一致，不改变数据模型和现有 `?w=` 服务端架构。

## 方案选择：自建 `?w=` vs `next/image`

结论：画布图片继续使用自建 `?w=`，`next/image` 仅用于普通 UI 图片。

- **鉴权**：Next 默认图片优化器不转发 Cookie/Authorization，受保护的 `/api/files/*` 会 401；要绕过只能 `unoptimized`，等于放弃优化。
- **缩放感知**：画布的缩放是 CSS transform，不是布局宽度变化；Next 的 `srcset` 选不中「当前缩放对应的档位」。
- **缓存语义**：现有 `?w=` 已有内容寻址、档位化、单飞、原子落盘、随源删除和一年 `immutable` 缓存，比 Next 的实例级磁盘缓存更可控、更适合多实例部署。
- **职责边界**：画布已有 `ImageLoadScheduler` 负责并发、优先级、中止与解码预热；引入 Next 优化器会形成两套加载语义。

## 业务规则

### 1. 显示 URL 契约

1. 节点 `data.src` / 多图 `multiResultKeys` 始终保存原始引用（存储 key 或外部 URL），**不得**写入带 `?w=` 的显示 URL；LOD 只存在于渲染期。
2. 对符合条件的托管图片，显示 URL = `fileRefUrl(src)` 的 `/api/files/{key}` 加上 `?w=<规范档位>`；其他查询参数与 hash 通过现有 `withManagedFileWidth` 保留。
3. 派生版本（`RESIZE_CACHE_VERSION`）**只存在于服务端对象 key**（`_cache/v2/...`），不进客户端 URL：`signed` 形态下版本段随对象 key 进入最终地址，浏览器缓存自然失效；`stream` 形态的版本失效边界见 [storage-signed-direct-delivery.md](storage-signed-direct-delivery.md) 规则 6.5。原规划的 `rv` 击穿参数已整体删除（2026-10-24 用户决策，从未进入提交）。
4. 调度器的探测 URL 与 `<img src>` 必须是**同一个字符串**，以保证探测命中的浏览器 HTTP 缓存被渲染复用。
5. 外部 `http(s)`、`data:`、`blob:`（上传预览）不追加 `?w=`，继续原样透传。
6. 视频海报由 `VideoNode` 显式构造 `?w=1280`；`CanvasImage` 的 LOD 为**显式 opt-in**，默认关闭，避免对已带 `w` 的海报重复改写。
7. 客户端只发送规范档位值；服务端的向上归一化仅作为防御，不承担 URL 稳定性的职责。
8. 逻辑 URL 上的 `w` 由访问描述接口转为派生请求参数（`POST /api/files/access` 的 `width`），最终地址由后端形态决定；派生缓存版本与签名 TTL 无关。

### 2. 适用范围与格式

1. v1 仅对「托管 URL + 路径扩展名为 `.png` / `.jpg` / `.jpeg`（大小写不敏感）+ LOD 显式开启」的图片生效。
2. 以下继续使用原图：
   - `.gif`、`.webp`、无扩展名或未知扩展名（动画正确性优先，且 v1 不引入动画元数据）。`.png` 中的多帧 APNG 由服务端识别并回退原图（规则 8.8）。
   - 外部 URL、`data:`、`blob:` 上传预览。
   - `ImageNodeData.pendingNaturalSize` 存在时的历史坏记录修复路径（见规则 9.3）。
3. 多图节点中的主图与非主图都适用同一规则；非主图通常没有可靠的自然宽度，按布局宽度计算即可。

### 3. 目标像素计算

1. 取图片在画布流坐标系中的布局矩形，复用 `placedImageRect` 与 React Flow `measured` 尺寸；节点测宽优先 `measured`，缺失时退回节点声明宽高。
2. 已知媒体宽高比 `aspect` 时，使用 contain 后的实际显示宽度：`cssWidth = min(rect.width, rect.height × aspect)`；未知时使用 `rect.width`。
3. `targetPx = cssWidth × zoom × effectiveDpr`。
4. `effectiveDpr = clamp(window.devicePixelRatio, 1, 3)`；浏览器缩放或显示器切换导致 DPR 变化时重新计算。
5. 自然宽度上限：
   - 若 `targetPx > 最大档位（2560）`：使用**原图 URL**。
   - 否则先取「大于等于 targetPx 的最小档位」；若已知 `naturalWidth > 0` 且该档位大于自然宽度，或 `targetPx >= naturalWidth`：使用原图 URL（避免请求比源图更大的派生档位，也避免同一内容生成多个等价缓存）。
   - 否则使用该档位。
6. 节点宽度为 0（既无 `measured`，也无声明宽高）时不发起图片请求，保持骨架；有任一可用尺寸即按规则计算。画布节点有显式宽高，测量不依赖图片本身——规则 3.1 的「缺失时退回节点声明宽高」优先于本条的等待，只有两者都没有才等待。
7. 初始缩放使用恢复后的视口 `getLiveViewport().zoom`，不得先按默认 1.0 请求一轮再切到 0.1。
8. 尚未加载过任何图片的节点（首次进入视口）在缩放手势进行中，使用 `min(实时 zoom, 已结算 zoom)` 计算首个档位，避免在缩放手势中启动高档位请求；已加载图片的换档仍只发生在结算后。
9. **缩小时中止在途高档位**：缩小手势中，若实时目标档位低于当前在途 job 的档位（包括有旧图占位时正在进行的更高档位升级），立即中止该在途 job（等价于把 lease 优先级置 `null`），结算后按最终档位重新加载。在途 job 为原图时按其 `naturalWidth` 参与比较，未知时视为高于最大档位。已就绪的显示图（含 stale 旧图）不消失；中止的只是在途 job。该规则只向下中止，不在手势中启动更高档位。

### 4. 档位表

1. 档位为：`64 / 112 / 200 / 300 / 320 / 400 / 480 / 640 / 960 / 1280 / 1920 / 2560`。
2. 新增 `640 / 960 / 1920 / 2560`，最大档位由 1280 提升为 2560；超过 2560 或达到自然宽度时使用原图。
3. 档位表、`normalizeResizeWidth`（向上取整、超过最大档取最大档）迁移到 `@noxrea/shared/media-tiers`，前端与服务端共同引用；不得在两个位置各维护一份字面量。
4. 既有调用点的 300 / 320 / 400 / 480 / 1280 保持不变；300 与 320 的近似重复不在本次合并，避免无关 URL 变化。
5. 服务端对 `?w=` 的归一化上限随档位表变为 2560；非法、缺失或 ≤0 的 `w` 维持现状（不缩放）。
6. 档位变化不改变 `?w=` 的语义：对图片是「要缩放」的信号，数值只是目标提示；最终档位由服务端按同一张表归一化。

### 5. 换档时机与滞回

1. **缩放结算**：监听 React Flow store 的 `transform[2]` 变化，尾随防抖 **200 ms**；手势进行中不为已加载图片发起换档请求，只保留现有图片；首次加载/首次进入视口按规则 3.8 用低档位启动，未就绪图片的降档中止见规则 3.9。
2. **节点尺寸结算**：图片布局宽度变化同样尾随防抖 200 ms；拖动节点（宽度不变）不触发换档。
3. **升级**：结算后的目标档位高于当前档位时，立即升级到目标档位（不再等待第二个窗口）。
4. **降档滞回**：仅当 `targetPx < 当前档位宽度 × 0.75` 时才降档到新的目标档位；否则保留当前档位，避免在边界附近反复请求。当前无档位时直接按目标选择。
5. **逻辑源变化**：`src`（逻辑引用）变化时立即清空档位状态，按新图片重新初始化；不得把旧图片的档位滞回带到新图片。
6. **离屏**：优先级为 `null`（不在视口与 240 px 预取边距内）时不发起新请求；重新进入视口时按当前结算值计算，不恢复历史档位。
7. **初始挂载**：不等 200 ms，直接使用恢复后的视口计算首个档位，避免「先原图、后档位」的双重加载。

### 6. 旧图占位（stale-while-revalidate）

1. 同一逻辑源因档位变化产生新的显示 URL 时，在新档位 ready 之前，`<img>` 继续显示**上一张已就绪的 URL**；不得回到骨架。
2. 骨架只用于：首次加载（没有任何已就绪图）、逻辑源变化（用户替换图片）、上传预览尚未就绪。
3. 新档位失败且存在旧图时，保留旧图，不弹出失败遮罩；下次缩放/尺寸变化时自然重试。无旧图时沿用现有失败态：警示图标 + 手动重试。
4. 旧图占位期间，`onLoad` 不重复触发；新档位就绪后替换 `src`，由调度器的探测解码与浏览器缓存减少切换闪烁，不额外做过渡动画。

### 7. 加载调度

1. `ImageLoadScheduler` 的并发容量由「4 个任务」改为「4 个重量单位」。
2. 任务重量由最终显示 URL 计算（`imageLoadWeight`，见技术影响）：
   - 档位 ≤ 1280：1。
   - 档位 1920 / 2560：2。
   - 无 `w` 的托管原图：3。
   - 外部 URL / `data:` / `blob:`：1（无法预知尺寸，保持现状）。
3. 调度器按「当前活跃重量 + 任务重量 ≤ 4」启动任务；重量取共享该 URL 的全部 consumer 的最大值。这样最多 1 张原图，或 2 张 ≥1920 档位同时解码。调度循环必须选择「优先级最高且能装下」的 job：活跃 3 时，重量 1 的 job 仍可启动，不能被重量 2 的排队 job 阻塞。运行中 job 若加入更重的 consumer，重量只升不降，允许活跃重量暂时超过容量但不再启动新 job，待回落；不得为重量升级重启已开始的解码。
4. 优先级、同 URL 共享、中止、60 秒超时、失败手动重试的语义不变。
5. 档位变化即 URL 变化，是新的 job；旧 job 失去 consumer 后按既有规则中止/删除，旧图占位不受影响。
6. 缩放手势中未就绪图片的降档中止复用现有「priority 置 `null` → abort」语义，不新增调度器取消 API；中止后结算时按新档位重新 `acquire`。

### 8. 服务端派生与缓存

1. 图片仍从原图直接缩放，不生成新的「图片母版」；sharp 池、单飞、原子落盘、`withoutEnlargement` 不变。
2. **EXIF 方向修复（同批必须实施）**：`produceImageWebP` 在 `resize` 前调用 `.autoOrient()`。
   - 已验证：Sharp 0.35.5 对带 `Orientation=6` 的 40×20 JPEG 直接 `resize` 输出 20×10，方向标签被移除但不旋转；加 `.autoOrient()` 后输出 20×40，与浏览器显示语义一致。
   - 不加此步，LOD 会把手机照片的缩略图方向显示错；现有 `?w=` 缩略图也有同样的历史问题，本次一并修复。
3. **缓存命名空间版本**：`_cache` 键升级为 `_cache/v2/<tier>/<源键 stem>.webp`。
   - 新代码只读写 v2；旧的无版本键 `_cache/<tier>/<stem>.webp` 属于历史遗留，不再解析、不再枚举、不参与按源删除，也不保留双读/双删兼容。
   - 旧键由部署迁移一次性清理（见「部署与迁移」）；清理前它们只是不可达的存储占用，不会被新请求命中。
   - 客户端不感知内部键形态；`signed` 形态下版本段随对象 key 进入最终地址，浏览器缓存键随之变化（见规则 1.3）；`stream` 形态的失效边界见 [storage-signed-direct-delivery.md](storage-signed-direct-delivery.md) 规则 6.5。
   - 版本升级的原因：缩放处理语义改变（auto-orient），不能继续复用可能方向错误的旧文件。
   - 版本段只存在于服务端对象 key；客户端 URL 只带 `w`，不追加版本参数，因此部署后画布外的既有缩略图 URL 不变（`signed` 形态由对象 key 变化自然回源；`stream` 形态按规则 6.5 的边界接受旧缓存）。
4. `DERIVED_KEY_PATTERNS` 只识别 `_cache/v2/...`；`derivedCandidatesOf` 只枚举 v2 档位前缀；`ownership` 只解析 v2。未来升级版本时，提升共享 `RESIZE_CACHE_VERSION`、先部署服务端、再一次性清理上一版本，不把旧版本加入运行期枚举清单；任何「同时兼容 N 个版本」的写法都视为架构退化。升级不改变客户端 URL（版本段在服务端），因此无需前后端发布顺序约束；`stream` 形态的浏览器旧字节边界见规则 6.5。
5. 视频海报档位与图片共用 `_cache` 与 `v2` 命名空间；海报母版来自 ffmpeg 抽帧，v2 重新生成不改变既有海报语义（本次 auto-orient 只加在图片缩放管线 `produceImageWebP`）。海报母版参数变化会改变档位内容；本次以 `RESIZE_CACHE_VERSION` 作为 `_cache` 的统一失效版本，未来不得只 bump `POSTER_VERSION` 而保留旧档位；若海报要独立演进，必须把 master version 纳入档位 key。
6. 503 / 429、`Retry-After`、媒体池过载语义不变；LOD 不引入「过载回退原图」的旁路。
7. 冷缓存首次访问：每个档位仍要从原图解码一次；NAS 2 核仅为开发观测，不作为设计上限，公网多实例下由媒体池/共享存储横向扩展。可能出现图片逐步出现（骨架持续数秒）；本 Spec 要求**帧率不受影响**，不把首次填充时间作为硬性门槛，按部署实测记录即可。预热已确认暂不做（见「已确认决策」）。
8. **APNG 正确性**：`.png` 可能是多帧 APNG，客户端无法仅凭扩展名识别。`produceImageWebP` 在缓存未命中时只对 `.png` 读取 PNG chunk 头（不整图解码），在首个 `IDAT` 前遇到 `acTL` 块即判定为 APNG；此时按「不支持静态派生」处理，抛出内部哨兵，`getResizedWebP` 捕获后返回 `null`，路由按既有图片失败语义回退为原图（不生成静态档位、不写缓存，且不按失败记日志）。不依赖 sharp/libvips 的 APNG `pages` 支持（该行为未验证）；chunk 解析只读长度/类型并 seek，不读大块数据，按文件边界/最大迭代次数终止，畸形 PNG 按非 APNG 处理（后续 sharp 失败走原图兜底），不得死循环。APNG 继续播放，不冻结首帧。
9. **质量与色彩**：图片档位沿用 `webp({ quality: 75 })`。验收在 1.0/DPR2 下与原图对比，若出现明显块状或文字模糊，调整质量参数并提升 `RESIZE_CACHE_VERSION`，不为个别图片加特殊质量分支。带非 sRGB ICC 的 JPEG 需在验收中对比颜色；若派生 WebP 与原图观感不一致，统一输出色彩空间并在 Spec 记录处理方式，不依赖浏览器差异。

### 9. 数据与持久化边界

1. 不修改节点 `data`、store、保存/恢复、撤销、SSE 同步；显示 URL 永不落库。
2. 导出、标注、裁剪、网格拆分、全景/多视角、下载、预览浮层、生成参考图继续使用原始 `data.src` / 原始 URL，不读取 LOD URL。
3. `pendingNaturalSize` 节点强制 LOD 关闭并使用原图：该路径会用 `img.naturalWidth/Height` 回写 `data.naturalWidth/Height` 并重定节点尺寸；若加载的是小档位，会把 64/200 px 误写成原图尺寸。修复完成后该标记消失，节点自然进入 LOD。该标记是历史数据修复路径，不是 LOD/URL 兼容层；保留到相关数据清理完成，本次不改其语义。
4. `handleMainImgLoad` 对其他节点不写自然尺寸；实现后补断言，确保 LOD 图片的 `naturalWidth` 不会污染节点数据。
5. 多图节点：主图可传入已知 `naturalWidth` 作为上限；非主图没有可靠自然尺寸时不设上限，由服务端 `withoutEnlargement` 兜底。

### 10. 失败、过载与可观测性

1. 新档位请求失败（404 / 429 / 503 / 网络错误）时，调度器仍只看到 `failed`，与现状一致；有旧图则保留旧图，无旧图显示失败态与手动重试。
2. 不新增自动重试；不吞掉失败。服务端过载仍由路由返回 503/429 与 `Retry-After`，前端行为不变。
3. 不新增监控依赖；沿用服务端 `logEvent("media", ...)`。前端可在开发构建记录档位选择（可选，不作为验收项）。

### 预期效果（按已验证的几何与实测数据估算）

- 600 px 宽节点、0.1 缩放：DPR 1 时目标 60 → 档位 64；DPR 2 时目标 120 → 档位 200。
- 91 张图片在 200 档位下约 2.4 MP（按 200×133 估算），解码位图约 10 MB；相对实测 152.6 MP / 约 610 MB 降低约 60 倍。低缩放拖动的主线程解码压力随之消失。
- 冷服务端缓存首次访问仍需逐张解码原图生成档位；帧率目标不变，图片填充时间单独记录。

### 不涉及

- 无数据库结构/迁移，无 API 路径/鉴权/权限变更，无节点数据字段变更，无 `data.src` 语义变化；新增的是一次性派生缓存清理迁移，不涉及业务数据。
- `w` 的服务端归一化上限由 1280 变为 2560，属于本 Spec 明确的行为变更；客户端 URL 不增加版本参数。
- 不改 `next.config` 的图片优化配置；不启用 Next 图片优化器。

### 后续性能补充（2026-10-24）

LOD 上线后，低缩放全节点可见时的拖动仍在两处产生与图片解码无关的每帧开销。两项都在本 Spec 的「首次拖动跟手」目标之内，按根因单独修复：

1. **`.connection-rail-dot` 移除常驻 `will-change: transform`**（`web/src/styles/globals.css`）。
   - 原状：每个节点轨道的圆点常驻 `will-change`，浏览器为其（连同父 Handle）建立独立合成层；0.1 缩放下全部节点可见，每帧平移要重算全部轨道层。
   - 处理：删除该声明。hover 跟随期间 `transform` 过渡会让浏览器自动提升合成层，不需要常驻（与 `.node-tilt` 的既有约定一致）。
   - 本 Spec 原「非目标」把该问题列为次要、另立任务；用户于 2026-10-24 决定按本条更新 Spec 而非回退改动，故此处记录为已完成项。
2. **`NodeTitle` 的中间截断改为共享 `ResizeObserver`**（`web/src/features/canvas/nodes/NodeTitle.tsx`）。
   - 原状：每个标题各建一个 `ResizeObserver`，并在 `useLayoutEffect` 里同步读 `clientWidth` 与 `getComputedStyle`。90 节点画布挂载时即 90 个观察者，且提交期读尺寸会把刚提交的 DOM 反复重排。
   - 处理：模块级单观察者分发（`observeClip`），回调直接用 `entry.contentRect.width` 作为可用文本宽度（不含 padding），不再读计算样式；首个回调即初始测量，此时布局已完成，不落在 React 提交期。截断结果与其对应原文一起存状态，原文变化时先显示原文（由 `overflow: hidden` 裁切），等回调写入新结果，避免渲染期读到旧文案的截断结果。
   - 量宽逻辑（canvas `measureText` + 头尾 2:1 交替回收）不变，只改变「何时、由谁触发」。
3. 这两项均不改变 LOD 规则、档位、URL 或调度语义，也不改变本 Spec 的验收口径。

## 部署与迁移（无向后兼容）

1. **发布顺序：服务端先升级。** 客户端 URL 只带 `w`，不含版本段，因此不存在「新前端 URL 命中旧服务端 v1 字节」的错配：`signed` 形态的最终地址由服务端按对象 key 签发，旧服务端只会签出 v1 对象；`stream` 形态下旧服务端写 v1、新服务端写 v2，浏览器按 URL 缓存（URL 不变）可能短期持有旧字节——由规则 6.5 的已知边界接受，不做前后端顺序约束。仍建议服务端先全量升级，使新请求全部落到 v2 派生。
2. **一次性清理旧缓存。** 服务端全量升级到 v2 后，执行一次迁移：删除 `_cache/` 下旧的无版本档位目录 `_cache/{64,112,200,300,320,400,480,1280}/`（仅这些历史档位前缀；不得触碰 `_cache/v2/`、`_posters/`、`_sprite/`、`_proxy/`、`_tmp/` 与源文件）。迁移必须：
   - 后端无关（本地存储与 S3 都通过存储后端 list/delete 实现）；
   - 幂等（重复执行无副作用），多实例只执行一次或并发安全；
   - 失败可重试并记录日志；未清理的旧文件不可达，只占存储，不影响正确性。

   这是可再生成的缓存清理，但仍属破坏性操作，执行前需用户明确确认（AGENTS 第六章）。迁移入口保持独立、最小；若只是一次性脚本且不再被版本升级流程引用，执行后删除，不留在运行期。
3. **CDN/反向代理缓存键。** 部署层必须按完整 URL（含查询串）缓存：`?w=` 不同档位必须形成不同缓存键。`signed` 形态的最终地址是带 `X-Amz-*` 的预签名 URL，天然按对象 key 分区；跨用户共享 CDN 缓存另立 Spec。
4. **版本升级流程。** 任何改变缩放像素语义的参数（auto-orient、quality、算法、档位含义、海报母版参数）都必须提升共享 `RESIZE_CACHE_VERSION`；流程固定为：提升常量 → 服务端全量发布 → 清理上一版本缓存。运行期只识别当前版本，不保留双版本分支。
5. **回滚。** 回滚到旧代码不保证复用旧缓存；按同一流程清理当前版本并让旧版本重新生成，避免两代缓存混用。回滚不是兼容层，不改变「只识别当前版本」的约束。
6. **旧 URL 不做兼容。** 版本段在服务端对象 key，客户端 URL 形态不变；`signed` 形态下旧派生对象（v1）只占存储、不再被新请求命中；`stream` 形态下浏览器可能短期持有旧字节（规则 6.5）。不保留旧 URL 兼容分支。

## 异常与边界

- **首次进入就是 0.1**：节点全可见，全部按低档位加载；这是本 Spec 的主场景。
- **恢复视口晚于首帧**：初始结算值取恢复后的 `getLiveViewport().zoom`，并在测量完成后才发请求；不按默认 1.0 预加载。若实现中发现 React Flow 首帧仍以默认值触发请求，必须在 provider 挂载/视口同步后再放行 LOD 请求。
- **浏览器缩放/外接显示器**：DPR 变化重新计算；滞回规则同样生效，避免在 1.25/1.5 等非整数 DPR 下抖动。
- **高缩放**：目标超过 2560 或取档后超过自然宽度时使用原图；此时视口很小，可见图片数量有限，原图并发被重量 3 限制为最多 1 张。
- **自然宽度缺失**（历史数据）：不做自然宽度上限；目标超过 2560 用原图，否则用档位，服务端 `withoutEnlargement` 兜底。
- **小图**：目标取档后超过自然宽度即用原图，避免请求比源图更大的派生档位。
- **EXIF 方向**：服务端 auto-orient 后再缩放；验收用带 `Orientation=6` 的 JPEG fixture 检查宽高与显示方向。
- **动画 GIF/动态 WebP**：v1 不启用 LOD，继续原图；不会因 sharp 单帧输出而把动画压成静态首帧。静态 WebP 同样走原图，属于已知覆盖缺口。
- **APNG**：`.png` 可能是多帧；服务端识别后回退原图（规则 8.8），不会冻结首帧。客户端仍会把 URL 当作普通 PNG 档位，实际收到原图；这是可接受的边缘成本。
- **外链图片**：`http(s)` 外链不经过本服务，无法生成档位；大量大尺寸外链仍可能全分辨率解码。这是已知覆盖边界，不通过服务端代理规避（SSRF、鉴权与缓存归属复杂），需要时另立方案。
- **右键另存**：画布展示的是当前档位，浏览器「图片另存为」会保存该档位而非原图；产品内下载/导出/预览仍走原图。若产品要求右键也拿原图，应在画布层统一拦截上下文菜单，不属于本次 LOD。
- **上传预览 `blob:`**：LOD 不介入；上传管道的撤销时点不变。
- **离屏/预取**：优先级仍按现有 240 px 边距；档位请求不会绕过优先级。
- **档位失败**：有旧图保留旧图；无旧图进入现有失败态。不会因为一次缩略图失败把整个节点标记为损坏。
- **服务端 503/429**：调度器统一显示失败/重试，不自动降级到原图（避免把过载变成带宽雪崩）。
- **非过载缩放失败**：sharp 不可用或格式不支持时，现有路由对图片仍回退为服务原图；这是既有行为，可能让单张图回到全分辨率解码。本次不改变该兜底；若验收发现高频失败，应单独处理，不得在 LOD 层静默吞掉。
- **缓存被禁用/逐出**：每个档位 URL 仍需重新下载；与现有 HTTP URL 渲染 Spec 的取舍一致。
- **旧缓存与一次性回源**：旧的无版本 `_cache` 在迁移中一次性删除，不再由源删除联动维护；新代码只读写 v2。升级后首次访问会重新生成 v2；服务端派生缓存会冷启动，形成一次性的缩略图回源波峰；媒体池的并发上限与 503/429 会自然削峰，但仍应在低峰发布并观察过载日志。这是版本化派生缓存的已知成本，不以兼容层规避。
- **`stream` 形态的版本失效边界**：`local` 后端的最终地址是源 key 上的 `?w=` URL，版本段只在服务端派生键，客户端 URL 不随版本变化。提升 `RESIZE_CACHE_VERSION` 后，浏览器可能在 `immutable` 生命期内继续使用旧派生字节。该边界按 [storage-signed-direct-delivery.md](storage-signed-direct-delivery.md) 规则 6.5 接受，不引入 `rv` 补偿。
- **存储增长**：按需生成，单图最多 12 个档位；低档位体积很小，大档位接近源图。旧 v1 由迁移删除，v2 当前无 TTL/容量上限，沿用现有派生缓存策略。
- **同源多档位重复解码**：冷缓存下，同一源被不同档位/不同用户同时请求时，各档位各自从原图解码一次；媒体池限流保证不压垮 CPU，但不消除重复解码。v1 不生成图片母版；若公网多用户压测显示这是瓶颈，另立 Spec 增加 `_display` 母版（一次解码，档位从母版派生），不在本次以兼容层或特殊分支处理。
- **画质/色彩**：派生 WebP 沿用 q75；验收在 1.0/DPR2 下对比原图。带非 sRGB ICC 的 JPEG 需确认颜色观感；若偏色明显，统一色彩空间并提升缓存版本，不在 LOD 层按图片类型加分支。
- **多实例部署**：档位键与 v2 版本段是确定性的，所有实例共享同一存储时自然一致；本 Spec 不引入实例本地状态。
- **手动输入 `?w=`**：服务端仍按共享档位向上归一化，最大 2560；不会因为客户端只发规范值而拒绝旧/非规范值。归一化结果随 12 档表变化（例如 500→640，原为 1280；2048→2560，原为 1280），不保留旧映射；调用方应使用规范档位。

## 验收标准

### 静态检查与测试

- 前后端档位表来自 `@noxrea/shared/media-tiers`，全库无第二份档位字面量；`normalizeResizeWidth` 单测覆盖 64/112/200/300/320/400/480/640/960/1280/1920/2560 与超限，并锁定行为变更：500→640、1281→1920、2048→2560、99999→2560。
- 目标像素单测覆盖：600 px 节点在 0.1/1/2.5 缩放、DPR 1/2/3 下的档位；自然宽度小于/大于目标、目标落在两档之间但上一档超过自然宽度、`targetPx > 2560` 回退原图。
- 缩放结算：连续缩放过程中不产生新 URL；停止 200 ms 后只产生一次目标 URL。
- 降档滞回：目标略低于当前档位时不降；低于当前档位 75% 时降档。
- 首次挂载：恢复视口为 0.1 时，首个探测 URL 为低档位，不为原图/1280。
- 换档占位：档位变化时旧 `<img>` 保持可见，新档位 ready 后再替换；逻辑源变化时回骨架。
- 资格判定：托管 `.png/.jpg/.jpeg` 加 `?w=`；`.gif/.webp`、外部 URL、`data:`、`blob:` 不加。
- `withManagedFileWidth` 的所有托管调用点产生稳定 URL（只含 `w`，不含版本参数）；`file-url.test.ts` 与调用点相关断言同步。
- 调度器：重量 3 的原图最多 1 张并发；重量 2 的大档位最多 2 张；共享 job 重量取最大值；原有优先级/中止/超时/重试用例全部通过。
- 手势降档中止：1.0→0.1 缩小过程中，未就绪的 1280 job 被中止且不启动新的高档位；结算后请求 200；已有 stale 旧图时在途高档位中止但旧图仍显示；高缩放下在途的原图 job 同样被中止。
- 服务端：`_cache/v2/...` 构造 ↔ 解析 ↔ 归属往返；旧的无版本 v1 键不被解析/枚举；旧缓存迁移删除旧 8 档目录且不触碰 v2/其他命名空间/源文件，重复执行幂等；EXIF 方向 fixture 输出宽高正确；APNG 多帧 fixture 不生成静态档位并回退原图；`?w=99999` 归一化为 2560。
- `pendingNaturalSize` 节点不启用 LOD，`data.naturalWidth/Height` 不被档位尺寸污染。
- lint、类型检查、相关测试串行通过（Vitest 单 worker；web 测试单独在 `web/` 下执行）。

### 浏览器实测（人工/CDP，记录数据）

- 参考画布：≥100 个节点、≥90 张图片、进入视口 0.1；刷新后首次拖动 ≥800 px。
- 基线（2026-10-22）：图片队列未排空时的首次拖动 p50 33.3 ms，队列排空后 16.7 ms；91 个媒体、152.6 MP。
- 目标：首次拖动 p50 ≤ 16.7 ms（允许测量噪声取整到 16.7/20 ms 两档），p95 ≤ 33.3 ms；无 >100 ms 的 long task；连续拖动目视跟手。
- Network：0.1 缩放下所有符合 LOD 资格的 PNG/JPEG 图片请求均带规范 `?w=`（`signed` 形态下发往 bucket 的最终 URL 由服务端签发，`w` 已折叠进对象 key 或已生成派生对象），且 600 px 节点、源图宽度 ≥ 200 时 `w ≤ 200`；这些图片没有原图请求；GIF/WebP/外链/视频海报按各自规则。缩略图总传输量显著低于原图（记录实际值）。
- 缩放换档：从 0.1 滚轮到 1.0 并停止；换档期间旧图持续可见，不出现整屏骨架闪烁；停止后 ≤1 个结算窗口出现新档位请求。
- 缩小换档：从 1.0 缩小到 0.1 时，未就绪图片在拖动期间不继续解码高档位；结算后显示低档位，已就绪旧图不闪骨架。
- 画质/色彩：1.0/DPR2 下 1280 档与原图缩放对比无明显块状/文字模糊；带非 sRGB ICC 的 JPEG 颜色观感一致；若不一致记录差异与处理结论。
- 可选（不作为硬门槛）：4× CPU throttle 下重复首次拖动，记录 p50/p95，确认低档位仍显著优于基线。
- 高缩放：缩放至 3–5，确认目标超过 2560 的图片走原图且显示清晰；可见图片数量与并发受控。
- 方向：上传/使用一张带 EXIF `Orientation=6` 的 JPEG，画布 0.1 与 1.0 下方向均正确。
- 非目标回归：GIF/WebP 仍按原图播放/显示；视频海报仍为 `?w=1280`；导出/标注/裁剪/下载产物仍为原图分辨率。
- 冷缓存：清空服务端 `_cache/v2`，并用新的浏览器 profile（或禁用缓存）重新进入同一画布；帧率仍满足上述目标，记录图片逐步填充时间（不作为硬门槛）。
- 无新增控制台错误；浏览器缓存命中时同一 URL 不产生第二次完整网络请求。

### 部署与迁移验收

- 发布顺序：服务端 v2 全量完成后才发布前端；验证新前端请求只命中 v2 派生缓存。
- 迁移：旧 8 档目录被删除，v2/海报/雪碧图/代理/源文件保留，重复执行幂等；本地与 S3 各一次。
- CDN/反代：缓存键包含完整查询串，不同 `?w=` 档位不共享缓存条目。
- `stream` 形态版本边界：提升 `RESIZE_CACHE_VERSION` 后，确认服务端新请求读 v2；浏览器旧字节按规则 6.5 接受，不演练「版本感知 URL」。
- 服务端容量（部署环境，不以 NAS 单机为上限）：按目标并发首次访问跑一轮；记录档位生成 p95、媒体池排队、503/429 比例；不得 OOM/崩溃，过载必须是可重试的 503/429。具体并发按部署容量设定并记录。

## 已确认决策（2026-10-22）

1. **档位扩展**：新增 `640 / 960 / 1920 / 2560`，显示上限 2560；目标超过 2560、或目标取档后超过自然宽度时回退原图。
2. **共享档位模块**：档位表与 `normalizeResizeWidth` 迁到 `@noxrea/shared/media-tiers`，前后端单一来源。
3. **EXIF 方向与缓存版本**：同批加入 `.autoOrient()`，`_cache` 升级为 `v2` 命名空间；旧 v1 不再由新请求读取。原规划的 `rv=2` URL 令牌已于 2026-10-24 整体删除（见 [storage-signed-direct-delivery.md](storage-signed-direct-delivery.md) 规则 6.5），版本段只在服务端对象 key。旧 v1 的具体清理方式由本版审核补充（见下），不改变已确认的 v2 方向。
